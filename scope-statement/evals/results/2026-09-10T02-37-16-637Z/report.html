# Compliance Module — Scope Statement

**Status:** Draft · **Date:** 2026-09-10

## 1. Purpose

The compliance module evaluates a customer submission against the regulatory requirements in effect at the time of submission and returns a verdict of **pass** or **fail**, together with the specific requirements that drove that verdict.

It exists so that submission acceptance is a deterministic, reproducible, and auditable decision rather than a manual review judgment.

## 2. In Scope

1. **Submission intake validation.** Accept a structured submission and confirm it is well-formed and contains every field the applicable requirements reference. A submission that cannot be evaluated is reported as such — not silently treated as a fail.
2. **Requirement resolution.** Select the requirement set in force for the submission, based on its effective date and jurisdiction, from a versioned ruleset.
3. **Rule evaluation.** Evaluate each applicable requirement and record a per-requirement result.
4. **Verdict derivation.** Reduce per-requirement results to a single `pass`/`fail`. A submission passes only if every applicable requirement passes.
5. **Result reporting.** Return the verdict plus a machine-readable list of failed requirements, each with a stable requirement ID and human-readable reason.
6. **Evaluation record.** Emit an audit record per evaluation — submission ID, ruleset version applied, verdict, timestamp — sufficient to reproduce the decision later.
7. **Deterministic behavior.** The same submission against the same ruleset version yields the same verdict, at any time.

## 3. Out of Scope

- **Authoring or interpreting regulation.** The module consumes a ruleset; it does not derive rules from regulatory text, and performs no legal interpretation.
- **Ruleset maintenance and publication.** Updating rules when regulations change is upstream (see A2).
- **Submission collection and UI.** Forms, uploads, customer-facing messaging.
- **Remediation.** It reports why a submission failed; it does not correct, auto-fill, or resubmit.
- **Post-verdict workflow.** Approval routing, escalation, manual override, appeals, notification.
- **Identity and document authenticity.** It evaluates submitted content, not whether documents are genuine or the submitter is who they claim to be.
- **Regulatory reporting and filing**, which may consume this module's audit records but is separate.
- **Retention and disposal** of submission data.

## 4. Interfaces

**Input:** structured submission (customer ID, payload, jurisdiction, effective date), plus an optional explicit ruleset version to pin the evaluation.

**Output:** verdict (`pass` | `fail`), ruleset version applied, failed requirement IDs with reasons, evaluation timestamp.

**Error case:** a submission that cannot be evaluated (malformed, missing required fields, or no ruleset resolvable for its jurisdiction/date) returns an explicit *not-evaluable* error, distinct from `fail`.

## 5. Assumptions

- **A1.** Submissions arrive already structured and parsed; no extraction from free text or scanned documents.
- **A2.** A versioned, machine-readable ruleset is maintained outside this module and available at evaluation time. **"Current regulatory requirements" is read as the latest published ruleset version whose effective date precedes the submission date** — confirm this, as it decides whether resubmissions are judged under old or new rules.
- **A3.** Requirements are independently evaluable; no requirement's outcome depends on another's result.
- **A4.** Evaluation is synchronous and needs no external service call at decision time.

## 6. Open Questions

1. **Which regulatory regime(s) and jurisdictions** at launch? Single vs. multi-jurisdiction changes ruleset-resolution complexity materially.
2. **Who owns the ruleset**, and on what process/cadence is it updated? This is the module's largest external dependency.
3. **Re-evaluation on ruleset change.** Must previously passed submissions be re-evaluated, or is a verdict final as of its evaluation date?
4. **Partial compliance.** Is binary pass/fail sufficient, or is a "conditional / needs review" outcome required? Current scope assumes strictly binary.
5. **Volume and latency targets**, which determine whether A4 holds.

## 7. Acceptance Criteria

- A submission meeting all applicable requirements returns `pass`.
- A submission violating one or more requirements returns `fail` and names every violated requirement.
- An unevaluable submission returns the not-evaluable error, not `fail`.
- Evaluations are pinned to a ruleset version and reproducible from the audit record.
- Every evaluation produces an audit record.

# Compliance Module — Scope Statement

**Status:** Draft · **Date:** 2026-09-10

## 1. Purpose

The compliance module evaluates a customer submission against the regulatory requirements in force at the time of evaluation and returns a single determination: **pass** or **fail**. It exists so that submission acceptance is a deterministic, repeatable decision made in one place, rather than an ad hoc judgment distributed across intake paths.

## 2. Objectives

- Produce a correct pass/fail determination for every submission it accepts.
- Apply exactly one, identifiable version of the requirement set per evaluation.
- Make each determination reconstructible after the fact: same submission plus same requirement version yields the same result.

## 3. In Scope

- **Submission validation.** Accept a structured customer submission, evaluate it against every applicable requirement, return the determination.
- **Requirement evaluation.** Execute the rules constituting the current requirement set, including rules depending on field values, cross-field relationships, and submission date.
- **Requirement set versioning.** Identify which version was applied to a given evaluation and record it with the result.
- **Result emission.** Return the verdict, the requirement set version applied, and the evaluation timestamp.
- **Rejection of un-evaluable input.** Distinguish "fails the requirements" from "could not be evaluated" (malformed, incomplete, unsupported input) and surface the latter as an error rather than a fail.
- **Audit record.** Persist enough of each evaluation to answer later: what was decided, against what rules, when.

## 4. Out of Scope

- **Authoring or interpreting regulation.** The module executes a requirement set it is given; legal interpretation and rule authorship sit upstream.
- **Sourcing regulatory updates.** Detecting that regulations changed and producing an updated requirement set is a separate responsibility (see §7).
- **Remediation.** No correcting, completing, or resubmitting a failing submission, and no advising the customer how to pass.
- **Submission intake and storage.** Transport, authentication, file handling, and persistence of the submission belong to the calling system.
- **Workflow after the verdict.** Notification, appeals, manual override, human review queues, downstream state changes.
- **Reporting to regulators.** The module supplies the audit record; filing is not built here.
- **Retroactive re-evaluation** of prior submissions against a new requirement set.

## 5. Inputs and Outputs

**Input:** a structured customer submission conforming to a defined schema, plus the evaluation date (defaulting to now).

**Output:** `pass` or `fail`, plus the requirement set version applied and the evaluation timestamp.

**Error output (distinct from `fail`):** an indication that the submission could not be evaluated, with the reason.

## 6. Assumptions

1. Regulatory requirements are supplied as a versioned, machine-readable requirement set; the module does not parse regulatory text.
2. "Current" means the requirement set marked active at the moment of evaluation. Effective-dated rules within that set are honoured against the evaluation date.
3. A submission arrives as a single structured payload — the module fetches no additional customer data.
4. Evaluation is synchronous and side-effect free apart from writing the audit record.
5. Determinations are advisory to the caller; enforcement is the caller's.

## 7. Open Questions

- **Which regulatory regimes, and who owns the requirement set?** The scope above assumes rules arrive from an upstream owner. If the module must ingest and interpret regulatory sources itself, that is materially larger work.
- **Is bare pass/fail sufficient?** A compliance decision that can't say *which* requirement failed is hard to defend in audit and impossible for the customer to act on. I'd recommend returning failed-requirement identifiers alongside the verdict; as written, the verdict stays the contract and that detail lives only in the audit record.
- **Mid-flight requirement changes** — is a submission pinned to the version at intake or at evaluation?
- **Retention period** for audit records.

## 8. Success Criteria

- Every accepted submission yields a determination or an explicit un-evaluable error; no silent passes.
- Each determination carries the requirement set version applied.
- A determination can be reproduced from the audit record.

## Objectives

## In Scope
