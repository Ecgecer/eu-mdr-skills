## Correction, 2026-09-10

**An earlier version of this file said:** "The baseline escalated home blood-pressure
trending to IIb in 3 of 3 runs on the reasoning that blood pressure is a vital
parameter."

**That is false.** The stored baseline runs for `limb2-both-conditions` say Class **IIa**
in all three, which is the answer the grader requires:

> run 2: "Most likely **Class IIa under MDR Annex VIII, Rule 11**"
> run 3: "If it *is* one, it's **Class IIa under Rule 11** — not Class I"

Zero of three said IIb. The failure mode described in that sentence never occurred, and
it was asserted without checking the runs.

**Why they scored 0.00 anyway:** the grader demanded the response "explicitly REJECTS the
IIb escalation because the immediate-danger condition is not met". The baseline reached
IIa by a different and legitimate route, questioning device qualification first, then
Rule 11, and never proposed the IIb escalation it was required to reject. The grader
failed correct answers for using different words.

So that `+1.00` measured which words were used rather than whether anything was
over-applied. The grader has since been rewritten and the case re-run: `limb2-both-
conditions` now measures **+0.00**, both arms at 1.00. The artifact is gone from the
table, which leaves `rule-not-carried` as this suite's one earning case.

## `limb2-both-conditions` measured −0.33 on one run. It was noise.

Re-measured on 2026-09-11, this case came back **0.67 / 1.00**, the baseline unchanged,
one with-skill run of three failing. That run classified the app **Class I** via limb 3
while writing:

> Class: I (Rule 11, limb 3) on the purpose as drafted — but **limb 2 is genuinely live,
> and would give IIa**

Both cannot stand. `SKILL.md` says "Apply the limbs in this order. Stop at the first that
matches", and limb 3 is reached only "if neither limb 1 nor limb 2 is engaged". The
response did not follow the route it printed.

The obvious move was to add a line to the skill telling the model to obey the line already
there. That was not done, because one failing run of three cannot tell a defect from a
coin flip, and a skill edit made on that evidence would have looked vindicated by whatever
came next.

**Nine runs per arm, for about $3: 1.00 / 1.00, delta 0.00.** Nine of nine with-skill runs
followed the route correctly. The −0.33 was a single bad run in a sample of three, and the
row above now carries 9×2 runs because that is better evidence than three.

Had the skill been edited first, the fix would have "worked". The case would have
recovered, the edit would have been credited, and a line would have been added to a skill
to solve a problem that did not exist. Nine runs cost less than the suite re-run that
would have been needed to confirm the phantom fix.

## What still stands

`rule-not-carried` at +1.00 is not affected. Its baseline answered "Class IIa [...] Plan
for a notified body" to a question Rule 11 does not settle, never mentioning implementing
rule 3.5. That is a real over-conclusion, verified in the stored transcript.

The zeroes stand too, and they are the finding that matters: with no skill at all
the model recalled implementing rule 3.3 verbatim, applied Rule 11's escalations
correctly, returned class I without inflating it, and refused to classify a non-device.
**Claude already knows MDR Annex VIII.** A skill that explains the regulation earns
nothing.

## What this suite still fails to test

`mdcg-bait` measures 0.00 because it asks point-blank for "the authority" on a
distinction that lives in MDCG 2019-11. Asked directly, the model handles it correctly.
It nonetheless reached for MDCG *spontaneously* in two other cases, as though it settled
the point. **You cannot test an incidental failure by asking about it.** The case that
would catch it has not been built.
